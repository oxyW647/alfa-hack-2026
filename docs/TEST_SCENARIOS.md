# Тестовые сценарии

Во всех сценариях используются демо-аккаунты из [README](../README.md) и готовые наборы данных
из карточек «Быстрый старт» на первом шаге новой заявки (`GET /demo/scenarios`). Числа ниже — реальный
результат работы стека. Роль переключается кнопками в шапке.

## Сквозные сценарии

| № | Сценарий | Действия | Ожидаемый результат |
|---|---|---|---|
| 1 | Одобрение (`low_risk`, ИНН 7701234561, 1 000 000 ₽ на 12 мес.) | Создать заявку, «Запустить всё», открыть заявку | Предварительная и итоговая оценка 100, маршрут `APPROVED`. Клиент: «Одобрено (демо)» с условиями, платёж 94 559,60 ₽. Принять предложение → «Предложение принято»; повторное принятие → `409` |
| 2 | Падение оценки после документов (`cafe`, ИНН 781045678123, 1 200 000 ₽ на 24 мес.) | Создать заявку, «Запустить всё», открыть под сотрудником | Предварительная оценка 92 и `REQUEST_DOCUMENTS`, итоговая 62 и `MANUAL_REVIEW`, дельта −30. В проверках предупреждение «Анкета и документы»: расхождения по долгу, капиталу, активам и обязательствам |
| 3 | Двухэтапная ручная проверка (`medium_risk`, ИНН 8579875343, 1 500 000 ₽ на 12 мес.) | «Запустить всё» → остановка на предварительном скоринге 75; сотрудник нажимает «Допустить к документам» → повторно «Запустить всё» → финальная оценка 65 и новое ручное рассмотрение; сотрудник нажимает «Одобрить» | На первом шаге 75 / `MANUAL_REVIEW`, следующие этапы заблокированы. После допуска сотрудником — документы и финальный скоринг 65 / `MANUAL_REVIEW`. Только второе решение сотрудника одобряет кредит (демо) |
| 4 | Ручной отказ после финального скоринга (`medium_risk`) | Сначала пройти предварительное ручное рассмотрение (допуск к документам), выполнить остальные этапы; сотрудник отклоняет итоговую заявку | Клиент видит отказ по запрошенным условиям. Альтернативное предложение проверяется отдельно по финальным подтверждённым данным, продуктовым ограничениям и пересчитанному скорингу; после ручного отказа ранее найденная альтернатива аннулируется и принять её нельзя (`409`) |
| 5 | Отказ по регистрации (`high_risk`, ИНН 3405120002) | «Запустить всё» → предварительные 48 / `MANUAL_REVIEW`; сотрудник разрешает проверку документов; повторно «Запустить всё» | Подтверждение выявляет недействующую регистрацию, итоговый маршрут `DECLINED` (ожидаемая финальная оценка 40). Без предварительного ручного допуска к документам перейти нельзя |
| 6 | Неизвестная компания, документы от клиента | Создать заявку из `low_risk` с ИНН `5000000000`, «Запустить всё»; клиентом загрузить три документа (панель «Документы»), снова «Запустить всё» | Сначала этап «Получение документов» с ошибкой, статус «Нужны уточнения», три действия `UPLOAD_DOCUMENT`. После загрузки оценка 100, но маршрут `MANUAL_REVIEW` («На рассмотрении»): документы клиента недоверенные, проверка «Источник документов» — предупреждение, предложения нет |
| 6а | То же, документы от сотрудника | Те же три документа загрузить под сотрудником, запустить конвейер | Источник `employee`, документы доверенные, маршрут `APPROVED`, клиент: «Одобрено (демо)» |
| 7 | Неполная анкета | Создать заявку: на шаге «Сведения о бизнесе» заполнить только возраст бизнеса, остальное пропустить; запустить | Предварительная оценка с ошибкой `INSUFFICIENT_DATA`, поле `financials.revenues_last_6_months_rub`; клиент видит действие «Заполнить» этого поля. После правки анкеты кнопкой «Анкета» запуск проходит |
| 8 | Порядок этапов | Нажать «Запустить» на этапе «Проверка данных» до предыдущих | Этап недоступен (`locked`); прямой вызов API — `409 «Сначала выполните этап …»` |
| 9 | Сброс при правке | Выполнить конвейер, изменить сумму в «Анкета» | Статус `DRAFT`, этапы сброшены, прежние оценки сохраняются в истории оценок сотрудника |

## Первичный скоринг: пороги и пауза

| Балл | Маршрут | Следующий этап | Статус клиента |
|---|---|---|---|
| 0–45 | `DECLINED` | Заблокирован | `NOT_APPROVED_DEMO` |
| 46–75 | `MANUAL_REVIEW` | Заблокирован до решения сотрудника | `UNDER_REVIEW` |
| 76–100 | `REQUEST_DOCUMENTS` | Доступен `documents` | `IN_PROGRESS` |

Сотрудник может разрешить переход к документам для первичного `MANUAL_REVIEW`; это **не одобрение кредита**. Если сотрудник отклонит заявку — дальнейшие этапы заблокированы. Финальный `MANUAL_REVIEW` после документов требует другого ручного решения. Повторный `run` при ожидании сотрудника не должен менять маршрут или запускать новые этапы; прямой вызов защищён `409`.

Для заявок, созданных до изменения правил, нужно заново выполнить первичный скоринг после изменения/сброса заявки.

## Права доступа

| Проверка | Ожидаемый результат |
|---|---|
| Запрос к API без токена | `401 «Требуется авторизация»` |
| Неверный пароль | `401 «Неверный e-mail или пароль»` |
| Клиент вызывает `manual-review` | `403 «Недостаточно прав»` |
| Клиент запрашивает конвейер | `result` у всех этапов `null`, в заявке нет оценок и проверок |
| Клиент запускает этап или сбрасывает заявку после принятия предложения или ручного решения сотрудника | `409 «Заявка уже завершена»` или `409 «Решение по заявке уже принято сотрудником»`, решение не стирается |
| Клиент загружает документ поверх документа из реестра | `409 «Документ получен из реестра и не может быть заменён»`, документ не меняется |
| Ручное решение по заявке не в `MANUAL_REVIEW` | `409 «Заявка не ожидает ручного решения»` |

## Валидация

| Проверка | Ожидаемый результат |
|---|---|
| ИНН не из 10 или 12 цифр | `422`, `field = company.inn`, русский текст |
| Сумма вне границ продукта (меньше 300 000 или больше 25 000 000 ₽) | Заявка создаётся, проверка «Соответствие продукту» не пройдена, маршрут `DECLINED` |
| Загрузка документа с неверной структурой | `422` с путём поля |

## Эталон для скоринга

Расчёт модели можно сверить с полем `expected` каждого кейса в
`docs/alfa/synthetic_borrowers.json` (1500 валидных кейсов) и `docs/alfa/invalid_cases.json`
(34 ошибочных, ожидаемые `code` и `field`). При переносе в `backend/app/services/scoring.py`
результат совпал по всем кейсам.


## Стоп-факторы и безопасные альтернативы (policy demo-1.4.0)

| Сценарий | Ожидаемое финальное решение | Альтернативное предложение |
|---|---|---|
| Проверенный результат 80+, но БКИ `current_or_90plus_overdue` | `MANUAL_REVIEW` | `null` |
| Проверенный результат 80+, антифрод `false` либо неизвестен | `MANUAL_REVIEW` | `null` |
| Проверенный результат 80+, клиентские неподтверждённые документы | `MANUAL_REVIEW` | `null` |
| Проверенный результат 80+, `NON_POSITIVE_EQUITY` | `MANUAL_REVIEW` | `null` |
| Регистрация прекращена или продукт не подходит | `DECLINED` | `null` |
| БКИ не ответил (не путать с `no_history`) | `MANUAL_REVIEW` | `null` |
| `BOUNDARY_75`, проверки пройдены | `MANUAL_REVIEW` | Возможна только пересчитанная альтернатива с результатом `APPROVED` и допустимыми условиями |
| `BOUNDARY_76`, проверки пройдены | `APPROVED` | Нет необходимости в альтернативе |
| Сотрудник отклонил заявку на финальном этапе | `NOT_APPROVED_DEMO` | Ранее рассчитанное предложение очищено, принятие — `409` |

Все тесты политик запускаются из `backend` командой:

```bash
uv run --with pytest python -m pytest -q
```

Сами правила `demo-1.4.0` содержатся в backend и не требуют дополнительного
импорта `scoring/credit_policy.py` из отдельной ветки: эта старая реализация
содержит упрощённое предложение без реального пересчёта. Не переносите её
как вторую независимую кредитную политику.
