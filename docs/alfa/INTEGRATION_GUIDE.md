# Как подключить скоринг: 

**Проект:** «Умный кредитный кабинет предпринимателя»  
**Комплект:** `v1.4`; алгоритм `MODEL_VERSION=1.2.0`, выходная схема `SCHEMA_VERSION=1.0.0`.  
**Интеграция:** прямой импорт Python-модуля. **HTTP API пока не существует**

## 1. Данные для Backend


Синтетическая информация не относится к реальным компаниям, людям, БКИ или банковским офферам. Значения `expected` — **ожидаемые выходы уже написанного экспертного алгоритма**, а не реальные кредитные исходы/метки дефолта.


Для самого скоринга нужны **четыре** раздела. `checks`, `registration_active`, `case_id`, `stage`, `business_profile`, `expected` не изменяют расчёт риска. Можно передать полный `case`, но в production следует сформировать явный входной контракт из разрешённых полей.

### Обязательные входные поля

| JSON-путь | Тип / единицы | Ограничение | Предполагаемый источник |
|---|---|---|---|
| `company.age_months` | целое число, мес. | `>=0` | Мок ФНС / проверенная карточка бизнеса |
| `loan.amount_rub` | число, ₽ | `>0` | Заявка |
| `loan.term_months` | целое, мес. | `>0` | Заявка |
| `loan.annual_rate_percent` | число, **проценты годовых** | `>=0`, например `24`, **не** `0.24` | Условия выбранного демо-продукта |
| `financials.revenues_last_6_months_rub` | массив **ровно 6 чисел**, ₽ за каждый месяц | все `>=0`; строго хронологический порядок | Финансовая история / мок |
| `financials.average_monthly_operating_expenses_rub` | число, ₽/мес. | `>=0`; платежи по кредитам **исключить** | Данные/отчётность |
| `financials.existing_monthly_debt_payments_rub` | число, ₽/мес. | `>=0` | Подтверждённые обязательства / мок БКИ |
| `financials.outstanding_debt_before_new_loan_rub` | число, ₽ | `>=0` | Подтверждённый остаток долга |
| `financials.equity_rub` | число, ₽ | может быть `<=0`; **отсутствие значения запрещено** | Метод определения капитала согласовать с аналитиком |
| `financials.current_assets_rub` | число, ₽ | `>=0` | Финансовые данные |
| `financials.current_liabilities_rub` | число, ₽ | `>=0` | Финансовые данные |
| `credit_history` | enum-строка | одно из пяти значений ниже | Подготовленная категория из мока БКИ |

Допустимые `credit_history`: `no_overdues_12m`, `no_history`, `closed_overdue_under_30`, `closed_overdue_30_89`, `current_or_90plus_overdue`. При ошибке получения БКИ не подставляйте `no_history`: это означает **подтверждённое отсутствие истории**, а не сбой источника.

**Содержимое JSON:** файл `data/synthetic_borrowers.json` — объект с `metadata` и массивом `cases`. Каждый элемент `cases[i]` содержит реальные поля входа (`company`, `loan`, `financials`, `credit_history`), данные демо-проверок (`checks`) и ожидаемый выход (`expected`). `business_profile` (форма `IP`/`OOO`, отрасль, город, `generation_stratum`) — **только metadata для выборки тестов, не финансовые признаки**.

Массив `factors` содержит шесть объектов. `score` — **балл, а не процент вероятности дефолта**; `main_risk_factors` содержит максимум три кода факторов в порядке потерянных баллов. `metrics` в отдельных сценариях могут содержать `null`. Также точный запрос, этот ответ и демонстрационный маршрут лежат в `examples/python_scoring_example.json`.

**Коды предупреждений:**
- `NON_POSITIVE_EQUITY`: капитал `<=0`; за Debt/Equity начислено 0, метрика `null`; демо-политика запрашивает ручную проверку;
- `NO_CURRENT_LIABILITIES`: при `current_liabilities=0` и `current_assets>0` начислено 15 баллов за ликвидность, метрика `null`; **упрощение MVP**;
- `NO_REVENUE`: шесть заполненных, но нулевых выручек; вариация выручки неопределена, 0 баллов за стабильность, метрика `null`.

**Ошибки, а не нулевые баллы:**
- `ScoringError.code == "INSUFFICIENT_DATA"` — отсутствует обязательное поле, неполные шесть месяцев, невозможен показатель `0/0` ликвидности;
- `ScoringError.code == "INVALID_INPUT"` — строка вместо числа, неверный тип, отрицательные показатели, неизвестный enum, неверное число месяцев и т. д.;
- `ScoringError.field` — путь поля для сообщения клиенту; метод `.as_dict()` сериализует `code`, `message`, `field`. У ошибок **нет** `risk_level` или `score`.

### Отдельные кредитные правила (демо)

Backend вызывает **после успешного скоринга**, с проверенными на сервере данными:

```python
from alfa_scoring import score_application, evaluate_demo_route

scored = score_application(application)
route = evaluate_demo_route(scored, application)
# route: {"route": "APPROVED", "reason": "...", "policy_version": "demo-1.2.0"}
```

Поля проверок берутся **из server-side моков/сотрудника**, не из пользовательского браузера:

```json
{"company":{"registration_active":true},"checks":{"documents_verified":true,"fraud_check_passed":true,"product_eligible":true}}
```

Логика демонстрационных статусов по порядку: неподтверждённые документы → `REQUEST_DOCUMENTS`; затем неактивная регистрация/недоступный продукт → `DECLINED`; затем антифрод/неположительный капитал → `MANUAL_REVIEW`; затем `score>75` → `APPROVED`; при 46–75 → `MANUAL_REVIEW`; при 0–45 → `DECLINED`. Это **пример**, требующий утверждения бизнес-аналитиком; нельзя выдавать за реальную политику банка. Названия статусов будущего конвейера Backend может определить отдельно.

### Повторная оценка и хранение

При уточнении документов (например, `CAFE_PRE` → `CAFE_VERIFIED`) backend должен создать **новый снимок** данных, сохранить предыдущие значения и новую оценку, сравнить балл **92 → 62**. Желательно хранить `application_id`, `assessment_id`, timestamp, источник/версию финансовых данных, `model_version`, `schema_version`, `score`, `breakdown`, `warnings` и отдельно `route`. Код скоринга **не имеет БД, API и памяти заявок**.

## Frontend — какие данные и экраны нужны

Frontend **не импортирует Python и не вычисляет балл**. Он отправляет анкету в API backend, отслеживает состояние заявки и показывает сообщения и доступные действия. **Имена HTTP endpoints и поля клиентского ответа пока не согласованы**; `examples/frontend_api_examples.json` — наглядный **проектный мок**, а не реализованный API.

**Путь клиента:**
1. Ввод суммы и срока → заполнение доступных финансовых сведений (список обязательных полей определяет backend и аналитик; не все бухгалтерские показатели обязательно вводятся вручную).
2. Сохранение анкеты и получение статуса «данные проверяются»; backend выполняет серверные проверки, при достаточных данных вызывает скоринг.
3. Нужны документы/данные → показать перечень недостающих полей и кнопку загрузки/исправления **внутри кабинета**.
4. После подтверждения → показать новый актуальный статус, а не сохранять в UI старое предварительное предложение.
5. Условия кредита и окончательное предложение показывать **только после подтверждения кредитной логикой backend**.

**Проектное соответствие маршрутов экрану:**

| Демо-маршрут backend | Предлагаемый `status` для клиента | Текст/действие |
|---|---|---|
| `REQUEST_DOCUMENTS` | `MORE_INFO_REQUIRED` | Уточнить сведения/загрузить документы |
| `MANUAL_REVIEW` | `UNDER_REVIEW` | Заявка на дополнительном рассмотрении |
| `APPROVED` | `APPROVED_DEMO` | Демонстрационное предложение; не считать выдачей средств |
| `DECLINED` | `NOT_APPROVED_DEMO` | Решение/альтернативные условия — только из backend |

**Два уровня объяснений:** для внутреннего кабинета сотрудника можно показывать `score`, `risk_level`, `breakdown`, `metrics`, `warnings`; для предпринимателя — согласованный бизнес-текст, статус и следующий шаг. Не стоит автоматически показывать все внутренние финансовые коэффициенты, кредитную историю или причины антифрод-проверки без продуктового согласования. `main_risk_factors` — коды, и фронтенду нельзя считать их готовым клиентским текстом. Если решено показывать балл, подпись — **«Оценка по демонстрационной модели, баллы из 100»**, но не «процент одобрения».

**Ошибки формы:** backend возвращает код и путь поля; фронтенд отображает локализованную ошибку рядом с соответствующим контролом (например, `loan.term_months`, `financials.revenues_last_6_months_rub`), но сервер обязан валидировать снова. При `INSUFFICIENT_DATA` пользователь должен иметь возможность дозаполнить заявку. Все запросы изменений статусов/документов остаются внутри приложения, без обязательных SMS/email.

**Фронтенду для моков нужны:** `examples/frontend_api_examples.json` (секция `expected_internal_scoring_for_QA_only` в этом файле — ВНЕ клиентского DTO и существует только для тестирования), `data/synthetic_borrowers.json` (выбрать тестовый `case_id`), этот раздел. Для сборки реального API требуется согласовать DTO, API routes, статусную машину и роль банковского сотрудника. Пока готов лишь Python-контракт вызова модели.

## 4. Как устроен расширенный датасет

- `data/synthetic_borrowers.json` — **1 500 корректных** заявок. **8 ручных контрольных кейсов** существуют в `data/curated_seed.json` (из них 6 валидны, 2 ошибочны); к валидным добавлены два специальных граничных кейса (`NO_CURRENT_LIABILITIES` и `NO_REVENUE`), 30 пар повторной оценки и 1 432 дополнительных разных профиля.
- `data/invalid_cases.json` — **34 ошибочных** запроса (32 сгенерированных мутации + 2 исходных кейса); каждый содержит `application` и `expected_error: {code, field}`.
- `data/dataset_summary.json` — статистика **самих синтетических** баллов/маршрутов и список 30 пар с баллами до/после.
- `data/curated_seed.json` — исходные восемь проверенных кейсов для повторного построения; это **не второй основной датасет**.

**Внутри валидного `case`:**

```text
case_id           — уникальный ID теста (для демо/QA)
borrower_id       — ID синтетического бизнеса; один и тот же у пары до/после
stage             — "preliminary" или "verified" (метка стадии, не переключает математику)
title             — человекочитаемое описание
business_profile  — legal_form/industry/city/generation_stratum; ТОЛЬКО демо-метаданные
company           — age_months для scoring; registration_active для demo_policy
loan              — amount_rub, term_months, annual_rate_percent
financials        — массив 6 выручек и 6 остальных финансовых полей
credit_history    — enum категории, выдаваемой моковым БКИ
checks            — 3 серверных демо-флага (НЕ доверять им из frontend)
expected          — score, risk_level, breakdown, warnings, route, вычисленные кодом
```

В генерации используются намеренно разные финансовые профили от устойчивых до стрессовых и условные ставки от 0 до 36% годовых. **Распределение не репрезентативно реальному портфелю банка.** Этот JSON нужен **для интеграции и тестов**, не для обучения кредитной модели и не для оценки её ROC-AUC.



`scoring.py` и `credit_policy.py` не требуют pip-зависимостей; **`pytest` нужен только для тестирования**. Для репозитория команды рекомендуется сохранить файлы исходника и фиксированную версию датасета. Скрипт генерации нужен для аудита происхождения тестовых данных.

## Вопросы, которые команде нужно согласовать 

- Кто формирует и подтверждает поля `financials`, как определяем `equity_rub` для ИП; есть ли шесть полных месяцев выручки?
- Как мок БКИ превращает просрочки в одну категорию и что делать при отсутствии ответа сервиса?
- Кто определяет продукт, срок, ставку и `product_eligible`; кому доступна ручная проверка?
- Действительно ли сохраняем предложенное упрощение по `current_liabilities=0` и капиталу `<=0`?
- Какие серверные и клиентские статусы утверждаются и какие данные можно показывать пользователю?
- Как backend версионирует повторные оценки и не показывает старое предварительное одобрение после ухудшения сведений?
